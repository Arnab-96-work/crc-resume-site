# Cloud Resume Challenge

A serverless resume website built on AWS, featuring a real-time visitor counter and fully automated CI/CD deployment pipeline.

## Live Site

[https://d1ujxbyfrpoq7k.cloudfront.net] (Resume Site)

---

## Architecture

```
Browser → CloudFront → S3 (static resume)
Browser → API Gateway → Lambda → DynamoDB (visitor counter)
```

| Service | Purpose |
|---|---|
| S3 | Hosts static HTML and CSS resume |
| CloudFront | CDN with HTTPS, caches S3 content globally |
| API Gateway | HTTP API endpoint for visitor counter |
| Lambda (Python) | Increments and returns visitor count |
| DynamoDB | Stores visitor count persistently |
| IAM | Least-privilege roles for Lambda |
| CloudWatch | Monitors Lambda errors |
| Terraform | Provisions all infrastructure as code |
| GitHub Actions | Automated CI/CD for frontend and backend |

## Infrastructure (Terraform)

All AWS resources are provisioned with Terraform. Console was used first to understand each service, then rebuilt as code.

**To deploy from scratch:**

```bash
cd terraform
terraform init
terraform plan
terraform apply
```

**After apply — copied these outputs:**
- `cloudfront_url` → paste into resume and LinkedIn
- `full_api_endpoint` → paste into index.html fetch call
- `s3_bucket_name` → add as GitHub Variable
- `cloudfront_id` → add as GitHub Variable
- `lambda_function_name` → add as GitHub Variable

**To destroy all resources:**

```bash
terraform destroy
```

## CI/CD Pipelines

### Frontend (`frontend_deploy.yml`)
Triggers when files inside `frontend/` change on a push to main.
1. Syncs frontend folder to S3 bucket
2. Invalidates CloudFront cache so changes go live immediately

### Backend (`backend_deploy.yml`)
Triggers when files inside `backend/` change on a push to main.
1. Zips `lambda_function.py`
2. Deploys zip to AWS Lambda

### GitHub Secrets Required

| Secret | Description |
|---|---|
| `AWS_ACCESS_KEY_ID` | CI/CD IAM user access key |
| `AWS_SECRET_ACCESS_KEY` | CI/CD IAM user secret key |

## Security

- S3 bucket is fully private — no public access
- CloudFront accesses S3 via Origin Access Control (OAC) with SigV4 signing
- Only the specific CloudFront distribution ARN can read from S3
- Lambda IAM role has minimum required permissions only
- AWS credentials stored as GitHub Secrets — never hardcoded
- CI/CD IAM user has restricted permissions — S3 sync, CloudFront invalidation, Lambda update only

## Key Decisions

**Why OAC instead of public S3?**
OAC ensures all traffic goes through CloudFront. Direct S3 access is blocked. Better security and forces HTTPS.

**Why PAY_PER_REQUEST on DynamoDB?**
Portfolio site has low traffic. PAY_PER_REQUEST costs nothing at low volume vs PROVISIONED which charges regardless of usage.

**Why HTTP API Gateway instead of REST?**
HTTP API is cheaper and faster for simple proxy integrations. REST API has more features but adds unnecessary cost and complexity for this use case.

**Why separate frontend and backend pipelines?**
Changing a CSS file should not trigger a Lambda deployment. Path filters ensure only relevant pipelines run on each push.
